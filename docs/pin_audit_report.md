Generated by `scripts/pin_audit.py docs/pin_assignments.csv`. Once it does, this script should be extended to parse its port list and cross-check against this table directly.

## Required human action before `.qsf` generation (M6)

`KEY[0:3]` and `SW[0:17]` are listed in the manual as **"Depending on JP7"** for I/O standard — not a fixed voltage like every other signal in this table (VGA/SDRAM/SD are all fixed 3.3V; LEDR is fixed 2.5V). **Do not guess the JP7 position.** The human team must physically read the JP7 jumper setting on the board (or consult Terasic's System Builder output for this specific board) before the `.qsf`'s `IOSTANDARD` assignments for these 22 pins can be written safely. This is flagged here and in `docs/known_limitations.md`, not silently defaulted to 3.3V.

## Known gaps in this audit (honest, not hidden)

- No top-level RTL file exists yet to cross-check port names/widths/directions against — only the planning CSV is validated for now.
- `SD_DAT[1]` and `SD_DAT[2]` are intentionally absent from the design (unused in SPI mode) — the script treats this as an expected warning, not an error, but a human reviewer should still confirm the board wrapper leaves those two pins safely unconnected/tri-stated rather than accidentally driven.
- This audit does not check timing, drive strength, or slew rate — those are Quartus pin-planner/timing-analyzer concerns, explicitly out of this project's scope (no synthesis tools are run).
